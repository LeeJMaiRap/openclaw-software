Mục lục
1. Tổng quan hệ thống
OpenClaw AI là một hệ thống đa agent chạy trên Docker Desktop, được thiết kế để tự động thực hiện các dự án phần mềm từ A đến Z — từ tiếp nhận yêu cầu của user, lập kế hoạch, phân bổ công việc, thực thi, kiểm tra cho đến báo cáo kết quả.
1.1 Triết lý thiết kế
Mục tiêu: Tự động hóa quy trình phát triển phần mềm: một user — một yêu cầu — một dự án hoàn chỉnh.
Nguồn cảm hứng: Lấy cảm hứng từ PM Agent (Microsoft) để định hình quy trình quản lý dự án cho LeeJ Agent.
Skill base: Dùng pm-skills repo (38 skills, khung Triple Diamond) làm nền tảng ra quyết định và tạo artifact.
Kiến trúc: Tách biệt lớp quản lý (LeeJ) và lớp thực thi (Worker) — tương tự CrewAI / AutoGen.

2. Kiến trúc hệ thống
2.1 Luồng chính (Happy Path)
User gửi yêu cầu qua Channel (Telegram / Discord / CLI).
LeeJ Agent tiếp nhận, hỏi lại để làm rõ mục tiêu, ràng buộc, stakeholder.
LeeJ chạy quy trình PM: tạo problem-statement → hypothesis → PRD → user-stories → task file.
Task file được giao cho Worker layer (có thể nhiều Worker chạy song song).
Worker thực thi, đẩy kết quả lên GitHub và ghi log vào Obsidian.
LeeJ kiểm tra chất lượng (edge-cases, launch-checklist) và báo cáo user.

3. LeeJ Agent — PM Core
3.1 Nguồn tham khảo thiết kế
LeeJ Agent được thiết kế dựa trên sự phối hợp của hai nguồn:
Nguồn 1 — Microsoft PM Agent Scenario
6 bước quy trình chuẩn: Thu thập → Phân tích → Cấu trúc BRD/PRD → Sinh spec → Feedback → Hoàn thiện.
Tập trung vào tính nhất quán của output (BRD/PRD chuẩn hóa).
Vòng lặp feedback với stakeholder trước khi hoàn thiện tài liệu.
Nguồn 2 — pm-skills repo (product-on-purpose)
38 skills theo khung Triple Diamond (Discover → Define → Develop → Deliver → Measure → Iterate).
Sẵn có MCP server (pm-skills-mcp) — LeeJ Agent gọi trực tiếp như tool call, không cần đọc file thủ công.
Giấy phép Apache 2.0 — có thể tùy chỉnh cho ngữ cảnh software agent.

3.3 Adapter Layer — Lưu ý quan trọng
pm-skills được thiết kế cho Product Manager con người. Khi áp dụng cho software agent, cần một lớp adapter tùy chỉnh:
Lọc bỏ: Rút gọn output của mỗi skill, chỉ giữ phần liên quan đến viết code.
Đổi ngữ cảnh: Chuyển sang chế độ “coding task” thay vì “product document”.
Task format: Dựa trên user-stories và acceptance-criteria làm input, không phải full PRD.
Phân tách: Từng Worker chỉ nhận một file task nhỏ, rõ ràng, độc lập.

4.3 Lộ trình khởi đầu đề xuất
Validate từng phần nhỏ theo thứ tự trước khi ghép toàn bộ hệ thống:
LeeJ Agent nhận yêu cầu → sinh task file đúng định dạng (bước quan trọng nhất).
Một Worker duy nhất đọc task file và thực thi thành công.
Ghi kết quả về Obsidian, kiểm tra định dạng và nội dung log.
Mở rộng ra nhiều Worker chạy song song.
Tích hợp Channel (Telegram / Discord) để user thực tế có thể ra lệnh.
5. Cấu trúc Task File đề xuất
5.1 Schema JSON
Mỗi task file mà LeeJ Agent sinh ra và giao cho Worker nên có cấu trúc sau:
{
  &quot;task_id&quot;: &quot;TASK-001&quot;,
  &quot;project&quot;: &quot;ten-du-an&quot;,
  &quot;goal&quot;: &quot;Mo ta muc tieu ro rang, co the do luong duoc&quot;,
  &quot;acceptance_criteria&quot;: [
    &quot;Tieu chi 1: cu the, co the kiem tra duoc&quot;,
    &quot;Tieu chi 2: ...&quot;
  ],
  &quot;constraints&quot;: [&quot;ngon-ngu&quot;, &quot;framework&quot;, &quot;gioi-han-cu-the&quot;],
  &quot;context_files&quot;: [&quot;path/to/relevant/file.md&quot;],
  &quot;worker&quot;: &quot;claude-cli&quot;,
  &quot;priority&quot;: &quot;high&quot;,
  &quot;timeout_minutes&quot;: 30
}
5.2 Tiêu chí “Done”
LeeJ Agent chỉ đánh dấu task là hoàn thành khi thỏa đủ các điều kiện sau:
Tất cả các mục trong acceptance_criteria được đáp ứng.
Output file tồn tại tại đường dẫn đã chỉ định.
Không có lỗi compile hoặc runtime.
Log đã được ghi vào Obsidian vault của dự án.
6. Kho tri thức — Obsidian Vault
6.1 Cấu trúc Vault
Mỗi dự án có một vault riêng trong Obsidian:
00-overview/ — Yêu cầu ban đầu, problem statement, goals của dự án.
01-tasks/ — Toàn bộ task file đã được LeeJ Agent tạo ra.
02-outputs/ — Kết quả thực thi của từng Worker (code, docs, test).
03-logs/ — Log hoạt động, lỗi phát sinh, quyết định của agent.
04-decisions/ — ADR — Architecture Decision Records.
05-retrospective/ — Retrospective và bài học sau mỗi dự án.
6.2 Phân vai giữa Obsidian và NoteBookLM
Quy tắc đơn giản: Obsidian là nơi agent ghi vào. NoteBookLM là nơi agent đọc ra.
Obsidian: Agent ghi log, task, decision vào Obsidian sau mỗi hành động.
NoteBookLM: Upload tài liệu tham khảo (spec, API docs) vào NoteBookLM để LeeJ Agent hỏi-đáp khi cần ngữ cảnh.

8. Bước tiếp theo
8.1 Ưu tiên ngay lập tức (Sprint 0)
